# 批次分類：一個 request 放幾筆

要對很多筆資料各做一次判斷時，可以把它們放進同一個 request、每筆一題。
這樣比逐筆送快十幾倍，也便宜一些，但**有上限**。

## 上限大約 20 筆

以逐筆送的結果為基準：24 筆以內完全一致，30 筆開始出現分歧，36 筆掉到八成，
48 筆只剩六成半。再往上會大量塌陷成同一個標籤 —— 模型已經認不出在問哪一筆。

保守取 20，在 code 裡切塊。

## 為什麼會壞

官方說批次不影響答案，但那是「**一份文件 + 多個問題**」的形狀：文件只付一次費，
每題各自對著它作答。

多筆資料、每筆一題是**不同的形狀**。批次時每一題都看得到全部資料，
其他筆對這一題而言就是無關內容，而 Jev 的準確度會隨著無關內容變多而下降。

## 用 confidence 監控

平均 confidence 跟正確率同步下降（24 筆時 0.81，48 筆時 0.57）。
所以不需要標準答案也能察覺劣化：**監控每批的平均 confidence，掉下來就把批次調小**。

## 規則不要移到 state

把分類規則放進 state、讓每題的選項不附描述，token 可以再省一半 ——
但實測 12 筆就錯了 2 筆。規則留在每題的 `criteria` 裡，省的那點錢不值得。

## 什麼時候不用批次

批次真正的價值是**速度**：一千筆逐筆送要跑約五分鐘，切成 20 筆一批只要十幾秒。

成本差距其實很小，逐筆每千筆約 $0.027、批次約 $0.018。
如果你的量不大又不趕時間，逐筆更簡單，也不必擔心上限和切塊邏輯。
